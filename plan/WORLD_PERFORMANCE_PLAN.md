# World 性能优化计划

## 简化原则

本计划只在不改变“每张地图由一个 Owner Node 单写”的前提下，减少无效工作。`World` 保留地图级互斥锁：移动、攻击、拾取等写操作按顺序执行，以保证位置占用和状态变更一致。

先测量真实瓶颈，再增加优化；不因理论上的并发问题提前引入 Zone Actor、细粒度多锁或分布式事务。本计划在 [GATEWAY_HA_PLAN.md](GATEWAY_HA_PLAN.md) 的多副本接入和会话租约完成后实施。

## 实施顺序

### 1. Gateway 轻量命令限流

按 `username + commandType` 在 Gateway 内存中记录最近一次已接受时间；超限请求直接拒绝，不进入 Node RPC。

建议初始阈值：

- 移动：50–100ms / 次
- 攻击：200–500ms / 次
- 治疗、购买：按秒限制少量请求

目的：防止单个客户端高频命令占满同地图的串行执行时间。

### 2. 最小性能观测

记录并按地图聚合：

- 各命令请求量与耗时；
- Node RPC 延迟与错误数；
- `World` 命令和 Tick 的执行耗时；
- 当前地图玩家数。

通过热点地图压测确认瓶颈位置；没有明确性能问题时，不继续增加并发复杂度。

### 3. 减少无变化的快照和推送

- 适当降低 Gateway 地图缓存刷新频率。
- 仅在 `World.version` 变化时更新缓存并推送地图状态。
- 操作结果仍立即返回给发起玩家；其余状态等待下一次地图刷新。

目的：避免无状态变化时重复构建、编码与发送完整地图。

### 4. 需要时再做简化增量同步

只有第 3 步不足以满足需求时才增加 `MapDelta`：

- 登录、重连、切图时发送完整 `WorldState`；
- 常态仅发送实体变更；
- 客户端版本不连续时直接接收完整状态，不维护 Delta 补发历史。

### 5. Node 仍为瓶颈时加入位置索引

在 `World` 中维护格子占用索引，将“目标格是否被玩家/NPC 占据”的查询从遍历实体改为 O(1) 查询。

保留地图级锁；登录、移动、死亡、复活、退出、NPC 刷新/死亡时同步维护索引。

## 当前不做

- Zone Actor、地图分区并发
- 玩家级、格子级多锁
- 跨分区原子移动
- 分布式事务与事件溯源
- Delta 历史补发与复杂重放机制

只有压测确认单地图 Node 写入吞吐无法满足目标时，才重新评估地图分区并发方案。
